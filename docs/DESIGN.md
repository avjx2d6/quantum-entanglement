# ТЗ: Quantum Entanglement Mod

**Платформа:** NeoForge, Minecraft 1.21.1
**Язык:** Java

---

## 1. Концепция

Мод воспроизводит старый ванильный баг квантовой запутанности предметов (два стака, разделявшие один объект в памяти) как осознанную механику с контролируемыми правилами.

Несколько физических ItemStack-ов — **окон** — принадлежат одной **сети** и разделяют общий **пул** количества. Каждое окно всегда показывает count = пул. Взял предмет из одного окна — количество упало во всех. Окна могут находиться в любых инвентарях, в любых чанках, у разных игроков.

Свойства предметов (имя, чары, данные модов) **не синхронизируются** — их изменение разрушает запутанность (см. §3.2). Игровая формулировка: *«квантовые предметы можно расходовать и использовать как ингредиенты, но изменение их свойств разрушает запутанность»*.

Термины:

| Термин | Значение |
|---|---|
| **Сеть** | Группа из 2–4 окон + пул. Идентифицируется `networkId` |
| **Пул** | Общее количество предметов сети. Единственный источник истины, живёт в SavedData |
| **Окно** | Физический ItemStack с компонентом `QuantumLinkData`. Показывает count = пул |
| **Plain** | Обычный предмет без связи |
| **Коллапс** | Разрушение запутанности из-за изменения свойств: изменённый стак забирает весь пул как plain, сеть растворяется |

---

## 2. Основной закон

Четыре правила, из которых выводится всё поведение инвентаря. Любой сценарий, не описанный явно, разрешается через них.

1. **Целый стак ездит со связью.** Перемещение окна целиком (shift-клик, swap с хотбаром, перенос курсором, выпадение из сломанного контейнера, смерть игрока) сохраняет `QuantumLinkData`.

2. **Отделение части = plain из пула.** Любая операция, отделяющая N **меньше пула** предметов от окна (ПКМ-сплит, drag по слотам, хоппер, Q), выдаёт **обычные** предметы; пул −N. Операция, забирающая **весь остаток** ради перемещения (Ctrl+Q, Q по последнему предмету, хоппер с последним предметом), отделением не является — это перемещение окна целиком по правилу 1: связь сохраняется, пул не меняется. Если же весь остаток не перемещается, а **потребляется** — приоритет у правила 4.

3. **Вливание plain = в пул.** Plain-предмет того же типа с теми же компонентами поглощается в пул (клик стаком, подбор) — но не выше `maxStackSize` предмета; излишек остаётся plain.

4. **Расход = из пула.** Съедание, использование как ингредиент крафта, переплавка в печи — обычный расход: пул −N. Результат (слиток, крафт) — plain. Расход последнего предмета опустошает пул — сеть растворяется: в отличие от взятия целиком, расход не перемещает окно, а уничтожает предмет.

## 3. Игровая механика

### 3.1 Создание и расширение сети

Блок **Quantum Entangler**, вход: стак из N предметов + **Quantum Shard** (расходуется).
Выход: **два окна** по N, пул = N. Это не дюп — суммарно доступно N предметов, просто из двух мест.

Расширение: окно + Shard → то же окно + новое окно той же сети. Пул не меняется. Максимум **4 окна**; каждое новое — за отдельный шард.

Ограничение: **только стакуемые предметы** (`maxStackSize > 1`). Предметы с прочностью в ваниле нестакуемы и не принимаются — иначе первый же удар инструментом (изменение компонента `Damage`) вызвал бы коллапс.

Каждое окно получает компонент и строку в тултипе:

```
Хлеб
Link ID: 001#1
```

`001` — сеть, `#1` — номер окна.

### 3.2 Изменение свойств = коллапс

Любое изменение компонентов окна (переименование на наковальне, зачарование, любые данные других модов) разрушает запутанность:

- изменённый стак выходит из сети как **plain со всем пулом** (count = пул на момент коллапса);
- пул = 0, сеть растворяется, остальные окна исчезают.

Количество предметов сохраняется: было доступно N — осталось N, в одном месте и без магии. Это осознанный баланс: одно неверное движение — и связи больше нет (как в оригинальном баге).

### 3.3 Сценарии инвентаря

Все выводятся из закона §2. Ключевая техническая опора: в 1.21 ванила складывает стаки только через `isSameItemSameComponents`, а компоненты окон различаются между собой (`#1` ≠ `#2`) и с plain-предметами — значит **ванила сама никогда не смержит окно ни с чем**. Половина сценариев не требует кода вообще.

| Сценарий | Поведение | Чем обеспечено |
|---|---|---|
| Два окна одной сети в одном слоте | Не складываются, swap | ванила (компоненты различаются) |
| Клик plain-стаком по окну (и наоборот) | Plain впитывается в пул до капа, излишек остаётся | `ItemStackedOnOtherEvent` |
| ПКМ-сплит (половина / по одному) | Отделённое — plain, пул −N | хук `split` |
| Drag по слотам | Каждый слот получает plain, пул −1 за каждый | хук `split` (через `Slot.safeInsert`) |
| Q (дроп одного) | Plain ×1, пул −1; последний предмет выпадает окном со связью | хук `split` |
| Ctrl+Q (дроп стака) | Окно выпадает целиком, связь сохраняется, пул не меняется | хук `split` |
| Хоппер тянет из окна | Plain ×1, пул −1; последний предмет уезжает окном со связью | хук `split` (через `ContainerHelper.removeItem`) |
| Хоппер толкает plain в слот окна | Не входит (в v1 не поглощает) | ванила (компоненты различаются) |
| Shift-клик, цифры, перенос курсором | Окно едет целиком, связь на месте | ванила (правило 1) |
| Подбор plain при наличии окна в инвентаре | Впитывается в пул до капа | `ItemEntityPickupEvent` |
| Двойной клик | Окна не собираются; сбор plain в окно-курсор — вне v1 | ванила |
| Окна разных сетей | Не взаимодействуют (swap) | ванила; перелив сетей — вне скоупа v1 |
| Съедание, крафт-ингредиент, печка | Пул −N, результат plain; последний предмет растворяет сеть | хук `setCount`/`shrink`; крафт последнего — событие крафта |

Общий принцип таблицы: как только операция забирает **весь остаток** пула, она перестаёт быть отделением и становится перемещением окна (правило 1). Например, ПКМ-сплит по окну с пулом 1 просто берёт окно в курсор.

### 3.4 Окна на земле

Окно попадает на землю целиком (Ctrl+Q, Q по последнему предмету, сломанный сундук, смерть игрока) — связь сохраняется (правило 1). Подбор — заходит целиком в пустой слот, связь на месте (домержить в существующий стак ванила не сможет).

Гибель ItemEntity (деспавн через 5 минут, лава, взрыв, кактус):

- окно **выбывает** из сети, пул не меняется — сгорело «окно», не предметы;
- если это было **последнее** окно — сеть и пул гибнут вместе с ним, предметы потеряны.

Частичный дроп (Q при пуле > 1) выбрасывает plain (§3.3), поэтому linked-предметы оказываются на земле только целыми окнами — с count = пул.

Балансовое следствие смерти: смерть ничего не «отправляет на базу» — предметы доступны из других окон с момента попадания в пул, а не с момента смерти. Умерший лишь рискует своим окном: не вернулся за 5 минут — окно деспавнилось, за новое надо платить шард.

### 3.5 Растворение сети (dissolve)

Сеть растворяется, когда пул = 0 (съели/скрафтили/переплавили всё, коллапс) или когда погибло последнее окно:

- все живые окна: strip `QuantumLinkData`, count = 0 → слоты пустеют;
- запись удаляется из SavedData;
- окно в выгруженном чанке: при загрузке `networkId` не найден в SavedData → strip, count = 0, слот пуст.

## 4. Технический дизайн

### 4.1 Архитектурный принцип

**Никакого шаринга живых объектов в памяти.** Пул в SavedData — единственный источник истины; окна — тупые носители `(networkId, memberId)`. Сервер *пишет* актуальный count в поле живых окон в момент изменения пула — чтение остаётся полностью ванильным, миксины на чтение не нужны. Синхронизация с клиентами происходит штатным диффингом меню (мы меняем поле — ванила сама разошлёт).

Обоснование: `ItemStack.copy()` вызывается повсюду (remoteSlots каждого открытого меню, превью наковальни/точила, ghost-слоты, рендер, чужие моды), идентичность стака нестабильна (пересоздание при сериализации и сетевой пересылке). Любая схема «два стака указывают на один объект» разваливается об это.

### 4.2 Компонент на предмете

```java
public record QuantumLinkData(int networkId, int memberId) {}
```

Кастомный `DataComponent`. Синхронизируется с клиентом автоматически вместе со стаком; тултип рендерится на клиенте из компонента.

### 4.3 Персистентное хранилище

`QuantumNetworks extends SavedData` — в `DimensionDataStorage` оверворлда, загружен всегда, от чанков не зависит.

```
Map<Integer networkId, Network>

Network {
    int pool;                       // общее количество, всегда >= 1
    Set<Integer> aliveMembers;      // живые номера окон, размер <= 4
    int nextMemberId;               // следующий выдаваемый номер
    Holder<Item> item;              // тип предмета
    DataComponentPatch snapshot;    // компоненты предмета БЕЗ QuantumLinkData
}
```

`setDirty()` при каждом изменении. `snapshot` фиксируется при создании сети и служит эталоном для валидации (§4.6).

### 4.4 Runtime-реестр канонических экземпляров

Server-side, пересоздаётся при старте сервера:

```
Map<(networkId, memberId), WeakReference<ItemStack>>
```

Правила (**last touch wins** — выяснено при реализации, что ванила легитимно подменяет экземпляры в слотах равными копиями при сетевых раунд-трипах и перезагрузке чанков, поэтому наказывать за несовпадение идентичности нельзя):

- операции с пулом применяются от канонического экземпляра; любая реконсиляция (split, сканы, подбор) **усыновляет** тронутый экземпляр как канонический;
- запись count в экземпляр при живом каноническом конкуренте (транзиентные копии: `copyWithCount`, симуляции извлечения) проходит в ванилу нетронутой — пул не участвует;
- дюп-защита обеспечивается не реестром, а самим пулом: извлечение математически ограничено пулом, сколько бы физических копий окна ни существовало;
- зачистка материализованных клонов (creative middle-click, `/give`) — только в рамках одного прохода скана: второй стак того же `(networkId, memberId)` за проход зануляется. Это косметика, не защита.

### 4.5 Точки перехвата

**Два маленьких mixin-а** (server-side, активируются только при наличии `QuantumLinkData`; мега-миксина в `AbstractContainerMenu.doClick` нет):

| Mixin | Логика |
|---|---|
| `ItemStack.split(int n)` | n < пул: отделённая часть strip → plain, пул −n, push count оставшимся окнам. n == пул (весь остаток): перемещение окна — возвращённый стак сохраняет связь, канонический экземпляр перерегистрируется на него, пул не меняется. Покрывает: ПКМ-сплит, drag (`Slot.safeInsert`), хопперы (`ContainerHelper.removeItem`), Q/Ctrl+Q (`Inventory.removeFromSelected`), `Slot.safeTake`. **Внимание:** split не отличает «взяли, чтобы переместить» от «взяли, чтобы уничтожить» — пути потребления целиком (крафт) закрываются отдельно, см. событие крафта и §7 |
| `ItemStack.setCount(int)` (сюда же `shrink`/`grow`/`consume`) | Дельта применяется к пулу, push всем каноническим окнам, `setDirty()`. Пул ≤ 0 → кламп в 0 → dissolve. Покрывает: еду, крафт, печку |

**События NeoForge** (без миксинов):

| Событие | Действие |
|---|---|
| `ItemStackedOnOtherEvent` | Клик plain по окну / окном по plain → впитывание в пул до капа |
| `ItemEntityPickupEvent.Pre` | Подбор plain при наличии окна того же типа → впитывание |
| `AnvilRepairEvent` | Изменение свойств при забирании результата → коллапс (превью не мешает — событие стреляет в момент take) |
| Событие зачарования за столом | Коллапс |
| `PlayerEvent.ItemCraftedEvent` | Линкованный ингредиент в сетке при пуле = 1 → предварительный расход: strip в plain, пул 0, dissolve — до того как потребление уйдёт в `split` целого остатка. Порядок события относительно потребления ингредиентов проверить при реализации |
| Загрузка чанка / BlockEntity | Реконсиляция инвентарей BE |
| `EntityJoinLevelEvent` (ItemEntity) | Реконсиляция предмета на земле |
| `ItemExpireEvent` / гибель ItemEntity | Выбытие окна; последнее → dissolve |
| `PlayerLoggedInEvent` | Реконсиляция инвентаря игрока |

**Реконсиляция стака** (единый алгоритм для чанков, сущностей, логина):

```
Найден ItemStack с QuantumLinkData(networkId, memberId):
    networkId есть в SavedData?
        нет  → strip, count = 0 (сеть была растворена)
        да   → валидация снапшота (§4.6); mismatch → коллапс
             → count = pool
             → регистрация в реестре канонических экземпляров
```

### 4.6 Валидационная сетка

Страховка от изменений свойств, для которых нет события (произвольные моды). При каждом касании окна в choke points (§4.5) и при реконсиляции сравниваем компоненты стака (за вычетом `QuantumLinkData`) со `snapshot` сети. Расхождение → коллапс.

Ключевое свойство: нам не нужно узнавать об изменении *в момент изменения*. Диверсировавший стак — это «plain, который ещё не оформили»; лениво заметить его при следующем касании безопасно. Коллапс идемпотентен: первый заметивший забирает пул и удаляет сеть, остальные окна зануляются правилом «мёртвый networkId → count 0». Дюп невозможен ни при каком порядке событий; худший исход пропущенного кейса — коллапс на несколько секунд позже.

### 4.7 Конкурентность

Сервер однопоточный, клики сериализуются — «два игрока взяли из одного пула» решается как в ванильном сундуке (у второго фантом, исправится синхронизацией меню). Растянутые во времени действия (двое доедают последний хлеб из разных окон): второй `shrink` клампится в 0 — худший случай «бесплатный укус», предметы не дюпаются. Дисциплина: **пул никогда не уходит в минус**.

## 7. Риски

| Риск | Митигация |
|---|---|
| Прямые записи в поле `count` мимо `setCount` в коде ванилы | Таких мест мало; аудит + реконсиляция выправляет count при следующем касании |
| Служебные копии стаков (remoteSlots, превью меню, симуляции) с компонентом | Записи count в копии проходят в ванилу нетронутыми; извлечение ограничено пулом |
| Модовые контейнеры на `ItemStackHandler` (частичное извлечение копиями в обход `split`) | Окно в модовой машине может «застыть» до следующей реконсиляции, но не задюпается; полноценная обёртка — будущая фаза |
| Паттерн ванилы «копия с нуля + grow» (`Inventory.addResource`: подбор, возврат курсора) | Миксин `Inventory.add`: окно переезжает целиком |
| Пропущенный хук гибели ItemEntity | Фантомный участник занимает слот из четырёх — неприятно, но не дюп |
| Пути «взять весь остаток и уничтожить» (потребление ингредиентов через `removeItem` → `split` целого) | Крафт закрыт `ItemCraftedEvent`; при реализации — аудит остальных потребителей (варочная стойка, торговля, станки, модовые машины). Незакрытый путь = потенциальный дюп последнего предмета, приоритет высокий |
| Обновления NeoForge ломают mixin-ы | Поверхность мала (2 метода ItemStack), чинится точечно |

## 8. Журнал решений

Зафиксированные развилки и почему выбрано именно так:

1. **Пул авторитетен, окна — носители ID** (вместо шаринга объекта в памяти из ранней версии ТЗ) — copy()-повсюду и нестабильная идентичность стаков делают identity-sharing неремонтопригодным.
2. **Свойства не синхронизируются, изменение = коллапс** (вместо синхронизации или белого списка действий) — единое правило, понятное игроку, одинаково честное для ванилы и любых модов; возвращает хрупкость оригинального бага как баланс; снимает самый хрупкий пласт реализации.
3. **Кап пула = maxStackSize предмета** — пул только убывает от сплитов; кап — это правило впитывания (`min(есть, cap − pool)`), а не отдельная механика.
4. **Частичный дроп = извлечение plain; дроп всего остатка = перемещение окна** — неинтуитивно, если смерть игрока и ломание сундука сохраняют связь, а собственный выброс её рушит. Цена решения: split целого остатка теперь означает «переезд», поэтому пути, где взятый целиком стак *уничтожается* (потребление в крафте), требуют отдельной обработки — иначе дюп последнего предмета (см. §7).
5. **Окно на земле сохраняет связь** — срыв связи при высыпании из сломанного сундука означал бы принудительное извлечение всего пула и молчаливое исчезновение остальных окон; сохранение связи проще в коде, безопаснее от дюпов и злее по балансу (деспавн последнего окна = потеря предметов).
6. **Гонки не чинятся сверх клампа** — сервер однопоточный; остаточные эффекты растянутых действий косметические.

## B. Зафиксированная доктрина (5 правил + привилегия)

Приняты автором в плейтестах («да, принимаю»). Универсальный безопасный fallback везде — **коллапс-в-plain**; инвариант железный: **никогда никаких дюпов и никакой пропажи предметов в никуда.** Хрупкость связи как *механика* — допустима.

1. **Окно никогда не свободный ItemEntity** → `cashOutToPlain` на `EntityJoinLevel`.
2. **Автоматизация двигает только plain**; последний предмет пула коллапсит на месте.
3. **Drag раздаёт plain из пула** (one-slot drag = положить целиком; multi = доли; creative-clone drag = cash out).
4. **Shift-клик** (`moveItemStackTo`) переносит целое окно в пустой слот, иначе коллапс; никогда не сливает через merge-drain.
5. **Creative-пакет**, заменяющий окно, ретайрит участника (без ghost-сетей).

**Привилегия игрока:** перенос окна целиком со связью (whole-take relocation) — только для жеста игрока (счётчик глубины `playerGestures`). Whole-take автоматизацией = `cashOut`; split живой копии = EMPTY.

**Открытый бэклог (task #23):** Create-compat модуль, где механическая рука сможет аккуратно нести окно (регистрируется как holder, каноничность едет с клешнёй, коллапс чистит её состояние; ленты остаются plain-only). Автор считает «рука несёт окно» символичной фичей; я запарковал её как отдельный модуль, т.к. клешня руки — приватное поле без канала уведомления, и заморозка происходит в коде Create, а не в нашем.

## C. Контент — зафиксированные решения (последнее обсуждение)

- **Мод = АРТЕФАКТ, а не логистика.** Сеть — редкая драгоценная штука (несколько на мир), а не инструмент автоматизации. Подтверждено автором.
- **Quantum Shard = редкий расходуемый лут-топливо.** Сжигается при создании/расширении сети — это было в самой первой идее мода. **Не автоматизируется** (фича киляет всё → добывать нельзя автоматом).
- **Источник шарда — Deep Dark / Ancient City** (тематика: вардены мешают лутать, «эффект наблюдателя»). Тюнинг: ~1–2 на разграбленный город, но **не брутально тяжело** — «не нужно слишком перестараться».
- **Entangler → мультиблочная структура** (один блок под такую махину выглядит «никчёмно»). Детальный согласованный дизайн — см. §G. Без жёсткой зависимости от Create.
- **Ponder-style сценки** — желаемы. Итог ресёрча + решение (см. §D).
- **Лор-рамка (автор):** Ancient City — пропавшая цивилизация с намёками на технологии; **осколки эха = остатки её технологий**; **скалк = зараза, которая её погубила** → скалк-блоки в наших рецептах/структуре НЕ используются (это была бы технология из заразы). Полированный дипслейт — материал города — наоборот, используется.

## D. Ponder — решение

Ponder теперь **отдельная standalone-библиотека**: `Creators-of-Create/Ponder`, maven `net.createmod.ponder` (репозиторий `https://maven.createmod.net`), **есть сборка под NeoForge 1.21.1**, Create как зависимость **не требуется**.

Регистрация сценок аддоном: реализовать `PonderPlugin`, зарегистрировать в client-setup; внутри `forComponents(<ResourceLocation предмета>)` привязывает сцену к предмету, `addStoryBoard(<путь .nbt>, <лямбда-раскадровка>)` задаёт сцену. Схематика: `src/main/resources/ponder/<category>/<name>.nbt`. Раскадровка — Java-инструкции (`showSection`, `showText`, `idle`, `rotateCameraY`, item-оверлеи).

**Решение (моё как со-автора, на согласование):**
- **Зависим от standalone Ponder** — хороший фит, низкий риск.
- **Рассказываем историю на уровне МИРА** (это ~80% концепции и родная стихия Ponder): сборка мультиблока → скорм шарда → вытянуть связанные копии → разложить по сундукам/бочкам в сцене → подпись «пул общий» → сломать связь → коллапс → автоматизация тянет plain. Несколько контейнеров + item-оверлеи + текст — Ponder делает это нативно.
- **НЕ расширяем Ponder ради GUI-сценок.** Пиксельная хореография слотов курсора (впитывание/дроб/shift-клик) — край механики, уже покрытый тултипами и осваиваемый «руками». Модель Ponder — мир, а не GUI-скрин; тащить туда инвентарные скрины = драться с инструментом (высокая цена, низкая отдача). Вывод: **кастомного кода Ponder, скорее всего, не нужно вообще.**

## G. Мультиблок — согласованный детальный дизайн (обсуждение 2026-07-16)

Автор задал каркас (свои блоки, крафты, пол, ритуал с выкладкой всех окон, сценарий анимации); я оформил детали. GUI **удаляется полностью** — всё взаимодействие в мире, на блоках.

### G.1 Блоки и предметы

|---|---|---|
| **Основа** (название финализировать; автору не нравится «матрица», нужно что-то более загадочное; кандидаты см. G.7) | крафт-компонент | центр — око эндера; левый + три верхних — эндер-пёрлы; правый + три нижних — осколки эха (4П + 1О + 4Э). Асимметрия пёрлы/эхо вокруг ока — намеренная |

### G.2 Структура

Пол **5×5 из аметистовых блоков**; на четырёх углах пола стоят резонаторы, в центре — ядро. Валидация — жёсткие офсеты от ядра (25 блоков пола + 4 резонатора), без вращений (симметрично). Скалка НЕТ (лор, §C).

```
. . . . .      R = резонатор (на углу), C = ядро (в центре)
. . C . .      кардинальные направления — свободные проходы
. . . . .
R . . . R
```

### G.3 Ритуал (взаимодействие без GUI)

- ПКМ стаком по резонатору → стак выкладывается (парит над блоком, рендер как у депо Create — ПКМ пустой рукой забирает). Реализация своя, у Create только подсмотреть UX.
- **Порядок строгий: сначала выкладка, потом шард.** ПКМ шардом по ядру = **немедленный запуск ритуала**, даже если резонаторы пустые. Никаких состояний ожидания.
- **С момента запуска все предметы заблокированы**: ни взять, ни положить (ни с резонаторов, ни шард с ядра) до конца ритуала.
- **Создание сети:** ровно ОДИН занятый резонатор с plain-стаком (два разных стака = провал — нет двусмысленности «что вход»). Итог: 2 окна за 1 шард (вход становится окном #1, окно #2 материализуется на пустом резонаторе).
- **Расширение сети:** на резонаторах должны быть выложены **ВСЕ живые окна этой сети** (заранее, до шарда). Не все выложены = провал. Итог: +1 окно за шард на пустом резонаторе. Сеть из 4 окон занимает все 4 резонатора → пустых нет → расширение физически невозможно: **кап 4 окна виден глазами**.
  - Почему «все окна на стол»: геймплей (сбор окон со всей базы/от других игроков = событие, риск транспортировки, «реко-герентность») + движок (все канонические экземпляры локально в загруженных BE → добавление участника атомарно, без удалённых окон и heal'ов).
- Провал (пустые резонаторы / нестакуемый предмет / нет пустого резонатора / лишние стаки / не все окна сети): красный финал анимации, **шард СГОРАЕТ**. Правила игрок обязан знать (их учит Ponder-сцена, §D); ошибся — сам виноват. Предметы на резонаторах после провала разблокируются нетронутыми.
- Экономика сети: создание 1 шард, каждое расширение 1 шард → полные 4 окна = 3 шарда (как в исходном ТЗ).

### G.4 Анимация и звук (машина состояний BE)

Сервер ведёт состояние (enum + возраст), клиент рендерит (BER ядра + эмиттеры частиц); синхронизация штатным BE-sync. Библиотеки не нужны.

`IDLE` → (шард положен = немедленный старт, предметы блокируются) → `CHARGING` ~2с (шард парит над ядром; потоки частиц от резонаторов к точке над ядром; ядро раскручивается; аметистовые звоны растущей высоты) → `JUDGEMENT` ~1с (потоки от **входных** резонаторов меняют цвет; сервер делает реальную проверку) → `SUCCESS` (перекрас потоков к **выходным**, вспышка, звук маяка + портала, запутывание, шард сгорает) | `FAILURE` (плавный уход в красный, дым, ядро тормозит, **шард сгорает**, предметы на резонаторах разблокируются нетронутыми) → `IDLE`.
